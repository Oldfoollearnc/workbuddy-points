# 发布流程

面向维护者：从「代码改完」到「Releases 页面出现新安装包」的完整步骤。
安装包是手动上传的，这里把每一步的命令和文案模板固定下来，避免每次现想。

---

## 0. 首次开源前的一次性清理

推公开仓库前先过一遍这张表，之后每个版本都不用再管。

| 检查项 | 怎么查 | 期望 |
|---|---|---|
| 凭证文件没入库 | `git ls-files \| findstr /i "session account.json points_config datasource"` | 无输出 |
| 运行时目录被忽略 | 看 `.gitignore` | `logs/` `.venv/` `build/` `dist/` `.workbuddy/` 都在 |
| README 截图是演示数据 | 打开 `docs/screenshots/*.png` | 余额是 62,520、项目名是「积分观测台」这类假数据 |
| 开发截图没混进去 | `git ls-files docs/shots` | 空 |

> **`docs/shots/` 里的 67 张开发截图含真实余额和项目名。** 已加进 `.gitignore`，但它们在旧提交里仍然存在，所以下面用「无父提交」的方式开一个干净的首次提交。
>
> **历史提交里仍然有旧截图和旧 README。** 只删文件不改历史的话，别人 `git log` 还能翻到。最省事的做法是开一个干净的首次提交：

```bat
:: 在当前分支上开一个无父提交的新分支，工作区内容不变
git checkout --orphan public
git add -A
git commit -m "chore: initial public release v1.7.1 [skip version]"
git branch -M main

:: 在 GitHub 建好空仓库后
git remote add origin https://github.com/Oldfoollearnc/workbuddy-points.git
git push -u origin main

:: 打 tag 并推送，Releases 页面以它为准
git tag -a v1.7.1 -m "v1.7.1"
git push origin v1.7.1
```

仓库描述建议：`Windows 桌面小组件：WorkBuddy 积分余额、消耗与逐笔流水看板`。
Topics 建议：`workbuddy` `desktop-app` `pywebview` `windows` `dashboard` `svg-charts`。

## 1. 改版本号

版本号只有两个来源，必须一致：

1. `version.json` —— 由 `.githooks/commit-msg` 按提交信息自动递增；
2. 编译安装包时的 `/DMyVersion` —— 手动传，必须等于 `version.json`。

```bat
git config core.hooksPath .githooks   :: 只需配一次
type version.json                     :: 确认当前版本
```

提交信息规则：`feat` 加次版本、含 `!:` 或 `BREAKING CHANGE` 加主版本、其余加修订号；写 `[skip version]` 则不动。

## 2. 打包

```bat
:: 1) 先跑测试
node tests\metrics.test.js
.venv\Scripts\python.exe -m unittest discover -s tests -v

:: 2) PyInstaller（产物 dist\WorkBuddyPoints\）
::    直接跑会在 dist 已存在时删掉整个目录，文件多时可能被安全软件拦；
::    稳妥做法是输出到独立目录再换回去：
.venv\Scripts\python.exe -m PyInstaller build.spec --noconfirm --distpath dist_build --workpath build_tmp

:: 3) Inno Setup（产物 installer\Output\WorkBuddyPoints-Setup-<版本>.exe）
::    <版本> 必须与 version.json 一致
"C:\Program Files (x86)\Inno Setup 6\ISCC.exe" /DMyVersion=<版本> installer\WorkBuddyPoints.iss

:: 4) 绿色版：把 dist\WorkBuddyPoints 压成 WorkBuddyPoints-<版本>-portable.zip
```

> ISCC 的 `/D` 参数不要从 bash 直接传（会被拆成"多个脚本文件名"），
> 用 Python `subprocess.run([...])` 以参数列表形式调用最稳。

Inno Setup 装在当前用户下时，路径改为 `%LOCALAPPDATA%\Programs\Inno Setup 6\ISCC.exe`。

改过引导图文案的话，先跑一次 `tools\make_installer_art.py` 再编译。

## 3. 本地验一遍

安装包至少过这四项，任何一项失败都不要发：

- [ ] 双击安装，向导中文正常、品牌图不糊
- [ ] 启动后托盘出现，单击弹小窗，展开进主界面
- [ ] **覆盖安装**：旧版装着的情况下装新版，登录态与历史数据还在
- [ ] 卸载后 `%APPDATA%\WorkBuddyPoints` 仍在（重装不用重新扫码）

## 4. 写更新说明

在 `CHANGELOG.md` 顶部加一段，只写用户能感知到的变化，按「新增 / 改进 / 修复」分组，每条一句话、不超过三行：

```markdown
## [1.8.0] - 2026-11-02

**新增**

- 支持按模型筛选积分流水

**改进**

- 首屏渲染时间从 1.2s 降到 0.6s

**修复**

- 修复跨年后消耗日历错位

**安装包**：`WorkBuddyPoints-Setup-1.8.0.exe`（12.4 MB）
```

不写内部重构、不写文件名、不写「优化了若干细节」这种没信息量的话。

## 5. 发 Release

先推代码和 tag（tag 必须在打包提交之后）：

```bat
git push origin main
git tag -a v1.8.0 -m "v1.8.0"
git push origin v1.8.0
```

然后 GitHub → **Releases → Draft a new release**：

| 字段 | 填什么 |
|---|---|
| Choose a tag | 选刚推的 `v1.8.0` |
| Release title | `v1.8.0` |
| Describe this release | 粘贴下面的模板 |
| Attach binaries | `installer\Output\WorkBuddyPoints-Setup-1.8.0.exe` |
| 其它 | 勾选 **Set as the latest release**；预发布才勾 Pre-release |

正文模板（发布页直接可读，不要求人点进 CHANGELOG）：

```markdown
## 本次更新

- 支持按模型筛选积分流水
- 首屏渲染时间从 1.2s 降到 0.6s
- 修复跨年后消耗日历错位

## 安装

下载 `WorkBuddyPoints-Setup-1.8.0.exe` 双击安装。已装旧版可直接覆盖，登录态与历史数据保留。

- 系统要求：Windows 10 1803+ / 11，x64
- 依赖 Microsoft Edge WebView2 运行时（Win10/11 通常自带）
- 首次使用：托盘图标 → 右上角头像 → 连接账号，扫码一次

完整记录见 [CHANGELOG](https://github.com/Oldfoollearnc/workbuddy-points/blob/main/CHANGELOG.md)。
```

## 6. 发布后

- 自己从 Releases 下载一次，确认文件名、体积、能装上（GitHub 偶尔会漏传大附件）。
- 需要校验值的话：

```bat
certutil -hashfile installer\Output\WorkBuddyPoints-Setup-1.8.0.exe SHA256
```

- 安装包没有代码签名，SmartScreen 会提示「Windows 已保护你的电脑」，点「更多信息 → 仍要运行」。这条可以写进 Release 正文，减少重复提问。
- 卸载反馈集中在 Issue 里，修完进下一个修订版本，不要在同一个 tag 上换包。
