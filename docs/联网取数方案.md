# 联网获取账号积分 · 技术方案

> 目标：把"本机消耗记录"升级为"账号级积分账户"，拿到余额、月周期、过期时间、每日与历史明细，并在程序中完整呈现。

---

## 一、要拿到的数据（按优先级）

| 优先级 | 数据                       | 用途         |
| --- | ------------------------ | ---------- |
| P0  | 总积分、剩余/可用积分              | 首屏 KPI、额度卡 |
| P0  | 本周期已用、周期起止（**按月**）       | 进度环、剩余天数   |
| P0  | 积分有效期 / 过期时间             | 到期提醒、避免浪费  |
| P1  | 每日消耗（含历史）                | 日历热力格、趋势   |
| P1  | 逐笔明细：时间、模型、倍率、积分、Token   | 流水页        |
| P1  | 按模型 / 按来源（对话、Agent、插件）汇总 | 构成图        |
| P2  | 套餐类型、加量包、账单记录            | 设置页账户信息    |

说明：本地 `rawUsage.credit` 只有"每次调用扣了多少"，没有余额与周期，也没有过期时间——这部分只能来自账号体系。

| 项      | 结论                                                                                                                                              |

## 三、三条可选路线

|       | A. 复用客户端登录态                  | **B. 应用内嵌登录（推荐）**               | C. 手动导入                 |
| ----- | ---------------------------- | ------------------------------- | ----------------------- |
| 做法    | 解密客户端 Cookies，直接带 cookie 调接口 | 应用自己开一个登录页，扫码后在同源页面里 `fetch` 接口 | 用户在官方用量页复制 JSON/导出，程序解析 |
| 数据完整度 | 最高                           | 最高                              | 取决于页面能复制到什么             |
| 首次成本  | 无需登录，但要做 DPAPI/Cookie 解密     | 需扫码一次（约 10 秒）                   | 每次都要手动操作                |
| 风险    | 读取其他程序的凭证，边界模糊；客户端加密升级即失效    | 凭证只存在本应用 profile，可控、可撤销         | 无                       |
| 稳定性   | 中（依赖客户端存储格式）                 | 中（依赖内部接口）                       | 高                       |
| 维护    | 高                            | 中                               | 低                       |

**推荐 B**：不动客户端任何数据，用户在应用内扫码，登录态存在本应用自己的 profile 里；之后所有请求都在同源页面内发起（自动携带 cookie），我们只接收 JSON。

## 四、推荐路线的实施步骤

1. **账号连接页**（新增，设置内）
   - WebView2 打开 `https://www.codebuddy.cn` 登录页，支持扫码/账密；
   - 检测到登录成功（cookie 存在且能拿到用户信息）后，标记"已连接"。
2. **接口探测（只读）**
   - 在已登录的同源页面里依次尝试候选路径，把**响应结构（不含敏感值）**&#x5199;入 `logs/api-probe.log`：
     - `/v2/user/cloudagent/quota`（已知存在）
     - `/v2/accounts`、`/v2/account`（已知存在）
     - 账号中心的 credits / billing / subscription 类路径（在登录后从页面 JS 里再抓一次）
   - 确认字段后固化成 1–2 个稳定请求。
3. **数据落库与合并**
   - 云端账户数据 → `cloud.json`（余额、周期、过期时间、每日汇总）
   - 本地逐次记录 → 继续作为"明细/模型/项目"来源
   - 两者在界面合并：**余额/周期取云端，明细与消耗构成取本地**，冲突时以云端为准并标注。
4. **刷新策略**：启动时 + 每 30 分钟 + 手动刷新；失败自动降级为本地数据，并在顶部显示"账户未连接/已过期"。
5. **凭证安全**
   - 登录态只存在应用自己的 WebView2 profile（`%LOCALAPPDATA%\WorkBuddyPoints`）；
   - 不写明文 token、不上传、不写入本项目代码库；
   - 只做 GET/只读，不做任何下单、兑换、切换账号的写操作。

## 九、最终实现（2026-10-21 晚，已跑通）

### 真正的数据接口（实测 200）

| 接口 | 方法 | 入参 | 返回 |
|---|---|---|---|
| `/billing/meter/get-user-resource-summary` | POST | `{}` | `TotalCredits`（可用总分）、`SubscriptionPackageName`（标准版）、`CreditGroups[]`（套餐基础/赠送/购买/奖励 的 总量/剩余/已用） |
| `/billing/meter/get-user-resource-free-packages` | POST | `PackageCodes` + 当天时间片 | 赠送/奖励积分包，含 `CycleStartTime` / `CycleEndTime`（**有效期**） |
| `/billing/meter/get-user-resource-paid-packages` | POST | `PackageCodes` + `Status:[0,3]` | 付费积分包 |
| `/billing/meter/get-user-request-usage` | POST | `startTime/endTime/pageNum/pageSize` | **云端逐笔扣费**：`requestTime`、`credit`、`model`、`client`、`agentPurpose` |

关键约束（踩过的坑）：

1. 必须是 **POST + `content-type: application/json` + `x-client-platform: web`**，用 GET 一律 401；
2. 会话**按页面加载刷新**——每次同步前必须先 `load_url(/profile/plans-usage)` 并等加载完成，否则 401；
3. 登录检测用 `GET /console/accounts`（200 即已登录），**不能用 `/v2/accounts`**（那个要客户端 OAuth Bearer，网页永远 401）；
4. 微信扫码的回调可能被外部浏览器接走 → 必须拦截 `window.open` 与 `target="_blank"`，强制同窗跳转。

### 界面映射

- 可用积分 = `TotalCredits`
- 已用 / 总额 = `CreditGroups` 汇总
- 有效期至 = 仍有余额的积分包里最早的 `CycleEndTime`
- 设置页新增积分包明细（套餐基础 / 套餐赠送 / 购买 / 平台奖励，带进度条）

### 已知限制

登录态是**浏览器会话级**，程序退出后需要重新扫码一次（已把 WebView2 配置目录固定到 `.webview-profile`，用于尽量延长会话）。这是本项目最不理想的一点，若要彻底解决需要客户端 OAuth，成本高且不稳定。

## 十、最终形态：扫一次码，以后免登录（已验证）

### 机制

```
首次：设置 → 连接账号 → 扫码
        ↓ 检测到 billing 接口 200
      拉取四个接口 → 渲染
        ↓
      CDP(127.0.0.1:9333) 导出 Cookie → DPAPI 加密 → session.bin
        ↓
以后每次启动：读取 session.bin → CDP 回填 Cookie → 直接同步
               （日志实测：restore_session: set 16 cookies → sync ok=True）
```

- Cookie 用 Windows DPAPI（当前用户绑定）加密，文件为 `session.bin`，换用户/换机器无法解密；
- 回填与取数都只在 `127.0.0.1:9333` 的本地调试端口内完成，不监听外网；
- 会话过期（一般数周）时会同步失败，状态变为「登录已过期」，点一次「连接账号」重新扫码即可，`session.bin` 自动更新。

## 十一、来源字段（client）与 WorkBuddy / CodeBuddy 拆分

### 为什么只能走云端

CodeBuddy 的本机数据里**没有**积分与 Token 明细，实测（2026-10-29）：

| 位置 | 内容 | 能否算积分 |
|---|---|---|
| `~/.codebuddy` | 没有 `projects/`，也没有 `workbuddy.db`（那是 CLI 的结构） | 否 |
| `%APPDATA%\CodeBuddy CN\codebuddy-sessions.vscdb` | `ItemTable` 两行：`conversationId / cwd / userId / title / status / createdAt` | 否 |
| `…\User\globalStorage\tencent-cloud.coding-copilot\` | 只有 4 个 .json（file-changes / genie-history / message-queue），不落消息与用量 | 否 |

两个客户端的 `userId` 是同一个（`a7bb22e8-…`），共用一份积分池：余额、额度、周期、有效期都是账号级，**拆不了也不需要拆**；
需要区分的只有"消耗"这条线。

### 探针：确认 `client` 到底有没有值

`account_service._probe_sources(bill)` 在每次同步成功后执行，只写结构不写内容：

实测（2026-10-30 00:02，本机真实响应）：

```
probe sources: rows=187 keys=agentPurpose,appType,client,credit,input,inputTrunc,model,requestId,requestTime,subscribeType
probe sources: client={"CodeBuddyIDE": 56, "WorkBuddy": 131}
probe sources: client×model={"CodeBuddyIDE|deepseek-v4.1-flash": 54, "CodeBuddyIDE|hy4-preview": 2,
                             "WorkBuddy|deepseek-v4.1-flash": 107, "WorkBuddy|wb-lite": 17, ...}
probe sources: client×purpose={"CodeBuddyIDE|": 56, "WorkBuddy|conversation": 105, ...}
```

结论：`client` 存在且能区分，真实取值是 **`WorkBuddy`** 与 **`CodeBuddyIDE`**（注意大小写与 IDE 后缀，
前端 `clientName()` 做了归一：`CodeBuddyIDE` → **CodeBuddy**，`WorkBuddy` → **WorkBuddy**）。
另一处差异：CodeBuddy 的 `agentPurpose` 是空串，流水「动作」列显示 `—`。

补拉完整窗口后（2026-10-30 00:10，886 条里 873 条带来源）出现第三个取值：

| client | 29 天积分 | 笔数 | 出现日期 | 处理 |
|---|---|---|---|---|
| `WorkBuddy` | 2,923.95 | 807 | 10-18 ~ 10-29 | → WorkBuddy |
| `CodeBuddyIDE` | 102.64 | 57 | 10-29 ~ 10-30 | → CodeBuddy |
| `app_cloud` | 5.63 | 9 | 10-19、10-21 | → App / 云端（看不出归属，单列不合并） |
| 空串 | 59.98 | 13 | 10-19、10-22 | → 历史（未标注），只出现在「全部」里 |

后端换过 `client` 取值也不用改代码：`clientName()` 对未知值原样显示，对 `*codebuddy*` / `*workbuddy*` 做归一。

落盘位置：`%APPDATA%\WorkBuddyPoints\logs\api-probe.log`。不写请求时间、不写单笔金额。

判定标准：

- `keys` 里出现 `client` 且取值 ≥2 种 → 可拆分，界面显示来源切换；
- 只有一个取值 / 没有该字段 → `cloudClients` 只剩一个空 id 的桶，`clientOptions()` 返回 `null`，界面**不显示**切换，
  维持"其它客户端（含 CodeBuddy）"的合并口径。

### 数据结构

```jsonc
// usageRows[] 每行新增 client（空串 = 历史行未标注，金额照常计入）
{ "id": "...", "t": "2026-10-28 17:45:00", "credit": 1.56,
  "model": "deepseek-v4.1-flash", "purpose": "conversation", "client": "codebuddy" }

// cloudClients：全量 29 天按来源聚合，前端日历/模型榜的唯一数据源
{ "codebuddy": { "points": 11.5, "calls": 2,
                 "days":   [{ "date": "2026-10-29", "points": 2.5, "calls": 1 }],
                 "models": [{ "name": "deepseek-v4.1-flash", "points": 2.5, "calls": 1 }] } }
```

聚合放在后端而不是前端从 `usageRows` 过滤：`usageRows` 有 1500 条上限，拿它算日历会在重度账号上悄悄丢历史。
